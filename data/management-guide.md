# 资料管理台使用说明

从首页右上角进入“资料管理”，或打开 `manage.html`。使用原有作品 ID，不另建重复档案。

1. 搜索中文名、原名、角色或作品 ID，选中作品；录入独立新作时点击“＋ 添加新作品”。

   新作品填写中文名、原名、首发年份、主／细分类、剧情简介、角色、玩法及各项来源，再填写一个原作内容与有确证的首批平台发行。同批平台逐行输入，共用一个内容 ID。系统建议尚未使用的作品 ID，并与主库、专题关联、仅专题书目和既有补录数据检查重名／ID 冲突。

   点击“将新作品加入修改清单”后，可继续补充四项叙事编目和创作者署名，随新作品一并提交。资料不足的编目可以暂缺，不能填占位词冒充已完成。普通移植或后发增补不能当独立原作录入；输入式书目的特殊准入仍走独立专题审查。

   同名独立作品需要额外身份核实，自动重复检查会阻止直接录入；存在并行补录导致的 ID 冲突时，保留草稿并重新核对，不能覆盖别人新加的作品。
2. 在“四项叙事编目”逐项填写结论、具体理由、资料摘记与来源。留空代表尚未核清，需要记录待核问题；最初八部历史基线只读。
3. 在“创作者署名”复用或新增个人身份，填写职责与版次范围。已有发行、库外产品与具名作品分工分别记录。勾选核实确认，再加入修改清单；既有署名订正通过补充说明单独审查。
4. “内容与版本”展示已存在的内容身份及历史发行。新发现的差异、角色补充和基础资料订正建议，在“补充说明”中附来源记录。这里不会自动新增正式内容版本或平台发行。
5. 表单输入自动存为本机草稿，但只有点击“加入修改清单”的记录才进入提交包。跨设备前点击“导出草稿”，在另一设备导入。草稿导入会检查记录冲突；与新数据库冲突的草稿必须重新核对，不强行覆盖。
6. 进入“审核与提交”，填写修改说明，检查每项修改前后的差异。点击“校验并准备 GitHub 提交”，复制更新包并打开 GitHub 提交页。
7. 登录有仓库写入权限的 GitHub 账号，选择 `main`，点击 **Run workflow**，将更新包粘贴到“资料管理更新包（JSON）”，运行。每批最多30项记录、60000字符；较大更新请分批。
8. 等待 Actions 运行完成，在运行摘要中打开 PR。如果仓库未启用机器人创建 PR，摘要会提供比较链接，手动点击 **Create pull request**。
9. 审核 PR 的 **Files changed** 后合并 `main`，等待 GitHub Pages 更新。失败步骤会显示原因，失败不会改写 `main`。

管理入口公开可访问；修改须经过 GitHub 登录与仓库写入权限。网页不索取、存储或嵌入 GitHub 令牌。更新包、修改历史和 PR 位于公开仓库，不要填写私密资料。

本机草稿不等于数据库已更新。PR 合并后请确认页面已更新，再清除本机草稿。后发增补版本、组织关系与历史身份订正仍需独立考据，不绕过现有保护规则。

## 本地使用更新包

在干净的独立分支运行：

```sh
python3 scripts/manage_catalogue.py path/to/update.json
python3 scripts/sync_versions_csv.py
python3 scripts/export_content_csv.py
python3 scripts/export_interaction_csv.py
python3 scripts/build_entity_model.py
python3 scripts/build_entity_pages.py

python3 scripts/audit_narrative_pending_20261030.py
python3 scripts/manage_catalogue.py --check
python3 scripts/validate_narrative_editorial.py
python3 scripts/validate_data.py
python3 scripts/validate_entity_model.py
python3 scripts/run_python_tests.py
node --test tests/*.test.mjs
python3 scripts/build_entity_model.py --check
```

管理历史逐项保存修改前后的值与来源。历史回归依此还原原审阅范围，同时单独验证当前数据；不会用重新冻结基线的方式掩盖历史修改。

## 基础库批量补录

从资料管理台点击 **从基础库批量补录**，或打开 [批量补录页面](../bulk-import.html)。基础身份库页面也有入口。

1. 页面实时读取 `main-adv-rpg-works-20261031.json` 和主库／专题关联资料，以名称、别名（NFKC）、外部来源 ID、已补录基础身份和年份交叉检查。可按年份、名称、别名或 VNDB ID 搜索；已有身份跳过，碰撞／年份冲突保留待核。
2. 勾选作品，可跨页选择，点击 **加入补录队列**。不会从品牌关联推断发行方，也不会把 ADV／Galgame 标签当作已核实的具体玩法。
3. 点击每部作品的 **填写／核对资料**，补充分类、剧情、角色、实际玩法与来源、原作内容依据、首批平台和实际发行署名，再勾选核对确认。四项叙事编目和个人创作者可后续在管理台完善。
4. 大批整理可点击 **导出本批资料模板／草稿**，在 JSON 的 `records[].values` 中回填各部作品的资料，确认后设置该记录的 `confirmed: true`；使用 **回填批量资料** 一次读入。保留 `identity` 对象、年份和基础身份。`platforms`／`characters`／各项来源使用换行分隔的字符串，`modes` 使用受控词表数组。文件最多500部、5MB；同身份更新，其他队列条目保留，文件有冲突时整份回填不生效。
5. 填写修改说明，点击 **校验本批并生成更新包**。任一作品缺项或冲突时先补齐或移除，再重新校验。所有作品通过后自动按每包最多30部、60000字符拆分，生成独立原作内容及其首批发行，共用一个内容 ID。
6. 依次复制每个更新包，打开 **GitHub 提交页**，选择 `main`，运行现有资料管理工作流；通过检查后审核 PR 并合并。前一包合并后再运行下一包，不能在不同设备同时使用同一批分配的作品 ID。并行写入或重复提交会被服务端拒绝，不覆盖已有档案。
7. 合并及 Pages 更新后，点击 **重新读取数据库**，核对该作品显示为已有身份，再从本机队列移除。草稿不等于已入库，重新读取不会自动删除队列。跨设备前导出资料模板／草稿。

补录记录附带 `basicRegistryId`、`titleAliases`、`sourceRefs`，供来源追踪、别名检索和重复提交检查。后端按当前基础库复核这些字段及年份，不能通过改 JSON 跳过已有身份或基础库内部碰撞。只有名称和年份的记录继续保存在基础身份层，不虚构平台、发行人、角色或原作内容。正式主库要求仍以 `content-model.md` 为准。

## 在主库页面直接修改与回撤

在首页“作品发现”打开正式作品档案，点击 **编辑作品／回撤最近3次修改**。高级发行检索卡片与资料管理台也提供入口。

- 可直接修改作品名称、原名、中文检索名及别名、分类／题材、简介、角色、玩法说明及来源、备注。填写修改说明和来源，预览差异并勾选核对后，点击 **保存到主库网站**。
- 首次需要连接具有该仓库写入权限的 GitHub 账号：在页面创建 Fine-grained personal access token，仅选择 `wt1234-donkey/visual-novel`，Repository permissions 中设置 **Contents: Read and write**。将凭证填入页面密码框后连接。凭证只保留在当前页面内存，不写入文件、URL、本机存储或修改记录；刷新或断开后需要重连。不要在聊天中发送凭证。
- 保存会直接创建 GitHub 提交，不再需要复制 JSON 或手动合并 PR。当前页面立即更新；GitHub Pages 发布完成后，其他设备刷新可见。页面不会把权限或网络错误当作保存成功；请求结果不明时会读取最新记录核对，不盲目重发。
- 每部作品独立保留最近 **3次成功保存** 的快照。下方“最近3次修改”列出修改说明、时间、操作者及差异；点击 **恢复到此次修改前** 可回撤该次及之后的修改。回撤也直接保存到网站，并增加修订号；较早记录仍可在 GitHub 提交历史追溯。新页面加载或跨设备读取的是同一份已保存历史。
- 多人／多标签页同时修改时，先检查作品修订，再以文件 SHA 原子写入。发生冲突时保留当前输入，请重新读取和核对，不覆盖他人的修改。
- 作品 ID、首发年份、内容版本和历史发行相互关联，仍通过原资料管理与版本考据流程处理。本入口以 `data/work-edit-history.json` 保存有来源的网页更正，首页与高级检索优先使用更正值；原始 `games.json`、历史专题及原始 CSV 仍保留原证据。别名去重同时读取网页更正，避免后续重复补录。不能把网页更正当作已完成新的版本／创作者考据。

较大修改请先保存自己的资料备份。网站修改说明、来源及历史位于公开仓库，勿填写私密信息。

### 自动带入基础身份资料

加入补录队列时，页面会自动带入基础库已经保存的名称、原名（若有）、年份、类型／玩法原文、玩法说明、来源链接和补充来源，并将关联品牌、年份依据、关联限定说明保留在备注。别名和 VNDB 等外部身份会显示在“已自动导入基础库资料”中，并随正式补录保存。

- 旧草稿点击 **补齐本批已有资料**；单部作品也有 **补齐本部已有资料**。系统只补空白或仍与上次自动导入一致的字段，保留手工填写的简介、原名、类型、备注等；自动补齐产生变化后需要重新核对确认。
- 基础库若已经保存完整剧情、角色、受控互动标签、原作内容依据及同一首批发行资料，也会复用这些字段。后发移植、混合发行方或不明确的首批记录不会自动拼成新原作。
- 对支持的 NextMoe 来源，可点击 **读取本部来源详情** 或 **读取本批来源详情（每次20部）**，根据基础库中的原来源链接读取已记载的原语言题名、附加题名和发布日期。先核对来源作品 ID、VNDB ID及年份，再补齐自动字段；不覆盖手工修改。来源异常、超时或身份／年份冲突会逐项提示，本机资料不丢失。
- 表单会显示“仍待补充”清单。基础库多数轻量记录并未保存剧情、主要角色、首发平台及发行署名；读取到的资料没有这些字段时继续留空，不从“Galgame／ADV”、品牌关联或发布日期猜造。
- 导出／回填模板会保留自动填入的字段状态和已读取详情，换设备后仍能区分手工内容与自动带入内容。该功能只处理作品元数据，不读取下载资源。
