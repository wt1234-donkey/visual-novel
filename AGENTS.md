# Repository and editorial rules

- All `visual-novel` changes, additions, pull requests, merges and Pages releases target **wt1234-donkey/visual-novel**. Do not write to `wwangtao833-dev/visual-novel` or synchronize changes back there.
- Read `data/content-model.md` before editing catalogue data. Schema v2 separates `works`, `contentVersions` and `platformReleases`. The old `versions` array must not be reintroduced, including inside related games.
- Preserve work identity, historical platform credits and source evidence. Existing historical releases with unknown content relationships stay `unverified`, with `contentVersionId: null`; do not equate unknown with identical or newly added content.
- A new work needs one original content record. A later content version requires specific, sourced additions and a comparison content ID. New story, character/route, playable area, art, music or recordings may qualify. Ordinary ports, translations, reissues, package changes, compatibility fixes and resolution increases alone do not.
- Future additions record only the first release batch of original/new content (`releaseRole: contentDebut`). Multiple platforms in that same batch reference ONE content ID. Do not append ordinary later ports just to expand the platform list.
- Leave the existing genre/command-game exceptions and historical publisher attribution in place.
- Regenerate both CSV indexes and dossiers. Required checks: `python3 scripts/validate_data.py`, `python3 scripts/run_python_tests.py` (hydrates committed historical snapshots in shallow checkouts), `node --test tests/*.test.mjs`, and `python3 scripts/build_company_pages.py --check`.
- Every main and related work must have nonempty `interactionModes`, `interactionNote`, `interactionBasis` and `interactionSources`; use the controlled labels in `taxonomy.interactionModes`. Read `data/interaction-model.md`. Assign multiple documented controls when needed, distinguish parser input / action menus / story choices / scene hotspots, and never infer playable combat from a battle-themed plot. Use the explicit `待核实` state if controls are unknown. Tags summarize known work-level play modes and must not be presented as uniform across all ports.
- After interaction edits run `python3 scripts/export_interaction_csv.py`, regenerate the other indexes and company pages, and keep the source/basis attached. Preserve the content-only future admission rule.
- New company dossiers use verified establishment dates after 1949, prioritizing companies already represented by actual catalogue releases without an existing dossier. New dossiers focus on narrative games and RPGs; do not expand them with pure daily-life training/raising, mahjong, board-game or pure competitive titles. Keep already published historical exceptions in older dossiers.

- Entity/participation migration: read `data/entity-model.md` before changing company, brand, developer, publisher or dossier relationships. Preserve original `publisher`, legacy publisher indexes and shared work/content/release identities. New scoped credits, entity identities and dossier membership live in the additive indexes generated by `scripts/build_entity_model.py`; do not infer a developer from a publisher or copyright signature. Keep unresolved identities/roles explicit.
- After changing entity rules or catalogue membership regenerate `build_entity_model.py`, `build_entity_pages.py` and `build_company_pages.py`; run `validate_entity_model.py` plus all existing checks and all three generators with `--check`. The entity migration baseline allows appended identities but protects existing objects; historical corrections need separate sourced review rather than silently rebasing. Keep all prior dossier URLs/anchors and five-year navigation semantics.
- Japanese entity display names use English/Latin spelling（日文）. Maintain `data/entity-display-names.json`, including transliteration/translation basis; regenerate the entity indexes and pages. Apply display names only after resolving historical credits. Preserve raw publisher fields, legacy filter values, entity IDs and old search aliases; a shared display label must never merge identities.

- Basic catalogue schema 3: preserve the reviewed checkpoint referenced by `journal.baseline` and append every future edit/undo through `src/domain/catalogue/model.mjs` with a unique operation ID, actor, reason and timestamp. Persist through `src/infrastructure/filesystem/basic-store.mjs` or the atomic GitHub repository adapter so the snapshot and event shards share one Git commit. Never patch current `records` without a matching journal event, reset the checkpoint or downgrade the stored format. Run `node scripts/migrate_basic_storage.mjs --check` for checksum and full replay verification; schema-1/2 fixtures remain supported. Full audit coverage starts at the recorded checkpoint, not at the beginning of repository history.
- The primary identity filename is now a shard manifest. Use `scripts/registry_store.py` or `src/infrastructure/filesystem/registry.mjs` for logical reads; Python writes must use `write_json`. Never recreate a monolithic tracked registry. Stage changed source shards with the manifest, preserve IDs and logical ordering, and run `python3 scripts/registry_store.py --check`.
- Current display values use `src/domain/catalogue/effective.mjs`, not separate page-specific overrides. Regenerate with `python3 scripts/generate_effective_views.py`; publication regenerates derived HTML and CSV automatically. Keep source facts and release/content identities unchanged. Follow `data/date-contract.json` for registered versus published years; do not turn future/unverified dates into shipped releases. See `docs/atlas-priority-five.md` for source leases and write boundaries.

- Release governance: `config/release-policy.json` declares public browser entries and user downloads. Register new pages/templates there, keep browser module dependencies complete, and build into a separate workspace before copying to the publication directory. Do not publish generators, tests, filesystem adapters, archived workflows or `editorial-service`. Run `scripts/validate_catalogue.py`; the same validation sequence serves release and intake candidates.
- Historical workflows in `archive/workflows/` are immutable and registered in `config/historical-tasks.json`; never restore their automatic triggers. Use `workflow_governance.py` to recover their fixed snapshot outside the repository and run registered checks. Register any new active yml/yaml workflow in `config/workflow-policy.json`.
- New source batches use `scripts/catalogue_intake.py` with a committed normalized source snapshot and a checksummed plan under `config/intake-plans/`, rather than copying dated import scripts/workflows. Keep stable external identities explicit, quarantine name/year/version ambiguity, and preserve existing identities. See `docs/release-governance.md`; explicit user instructions take precedence over default batch choices.

- Formal corrections use schema 2 in `data/work-edit-history.json`. Preserve the reviewed checkpoint registered in `config/formal-audit-checkpoint.json`; append every subsequent edit, creator-name change and undo through `work-edit-model.mjs`. Snapshot and event must be committed atomically, together with the trusted command receipt. Never prune events to the three-entry quick-undo window or reset the checkpoint. Run `node scripts/migrate_formal_history.mjs --check` for replay and checkpoint verification. Schema-1 fixtures remain readable; do not invent missing pre-migration events. See `docs/formal-audit.md`.

- Source/identity separation: read `docs/source-identities.md`. Preserve the immutable source prefix in `config/source-identity-baseline.json` (108,173 rows, original IDs/order/evidence) and append future sources through the registry adapter. Four separate types live in `src/domain/catalogue/source-identities.mjs`; raw row counts, provisional identity counts and explicitly resolved targets are different denominators. Names/years or shared external references generate candidates, never automatic identity links. Explicit decisions and independent undo events append to `data/source-identity-decisions.json` via the trusted command executor with one atomic receipt; never reset its revision or patch current links without replayable events. Formal profile IDs attached through basicRegistryId retain the existing source work identity. Run `node scripts/migrate_source_identities.mjs --check`; register new public entries in the release allowlist and keep identity directories sharded and original evidence on demand.

- Field evidence: read `docs/field-evidence.md`. Optional assertions, explicit selections and independent undo events live in `data/field-evidence.json`. Never overwrite a claim or source fact, auto-select by collection time, merge same-name subjects, or require evidence for the existing manual creator-name command. Validate exact work/content/release scope and existing source/entity/person IDs. Current pages, searches and exports use the shared field projection; ordinary edits must not copy pinned selections into legacy corrections. Run `node scripts/build_field_evidence.mjs --check` and regenerate `--export`; receipt and journal must be one trusted commit. Keep new targets indexed on demand and retain all source records, IDs and historical role/content relationships.
