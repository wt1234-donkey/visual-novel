# 正式作品编辑审计

正式编辑仍通过既有可信保存入口直接提交，不增加人工审核。作品身份、原作年份、内容版本和平台发行继续由各自领域规则管理；仅添加剧作、美术、音乐姓名仍不要求补充来源。

## 迁移范围

`data/work-edit-history.json` 的 schema 2 保留原 `records`，增加完整追加日志。`journal.baseline` 是迁移前已核当前更正及旧最近记录的原样检查点。检查点的时间、源提交及规范化 SHA256 登记在 `config/formal-audit-checkpoint.json`，普通保存不能修改它。

完整事件覆盖从这个检查点开始。旧最近记录继续展示为兼容证据，更早的历史可从 Git 查找；缺少完整依据的旧修改没有补造为事件。迁移本身不增加作品、更改有效值或重新解释内容和发行身份。

## 修改、撤销与查询

每个新事件包含独立操作 ID、作品 ID、全局顺序、前后作品修订、操作人、时间、说明、来源、完整可编辑字段前后值及更正状态前后值。姓名修改与普通修改共享追加路径。

每部作品的最近3次记录继续提供快捷回撤。恢复到某次修改前会撤回该次及之后的快捷修改，但完整事件不会删除；撤销自身追加一个新的事件，引用准确目标 ID，并保留操作人、时间和说明。修订号始终递增。

编辑窗口的“完整审计历史”每页显示20个事件，可继续查询更早记录。迁移检查点保留的旧记录单独说明覆盖边界。查询不依赖最近3次列表，也不需要扫描 Git 历史。

本批完整日志与快照保存在同一文件，保证一次 Git 提交同时落库。容量分片和操作索引属于第8批；目前未以容量优化为由删除或轮换事件。

## 中断与重试

可信保存继续使用第2批的不可变命令及统一回执。未确认的正式命令在当前浏览器会话中保留原操作 ID、时间、期望修订和来源凭据；凭证只在内存中，不进入待确认命令或历史。

点击“核对上次保存结果”时，先按原命令查回执。已经保存的命令返回原操作的修订和包含该操作的提交证据，读取当前最新状态；不会再次应用旧字段。即使已有其他修改、来源或规则已更新，也只确认原操作。未应用的旧命令仍须通过来源与修订检查，不能覆盖后来修改。

同一操作 ID 配上不同内容会被拒绝。只有明确发生在写入前的冲突才可释放该待确认命令；响应不明时保留原命令。浏览器会话存储不可用时，原命令仍在当前页面内存中可重试。

## 验证

- `node scripts/migrate_formal_history.mjs --check`：检查固定迁移起点、完整日志回放和当前状态相等。
- `python3 scripts/validate_work_edits.py`：核对当前值、兼容记录、追加事件和撤销语义。
- `node --test tests/formal-audit.test.mjs tests/work-edit.test.mjs tests/trusted-command.test.mjs`：跨页完整性、撤销、幂等与并发验证。
- `node --test tests/browser/*.test.mjs`：真实 Chromium 的完整历史、可信撤销、保存响应丢失、其他编辑者后续修改及刷新后重试。

`scripts/validate_catalogue.py` 和可信保存工作流都执行正式审计检查。服务器在提交前使用同一正式命令应用函数，不信任浏览器提供的当前快照。
