# 第1批：发布一致性与状态闭环

## 发布快照与恢复

`data/catalogue-release.json` 将基础目录、详情、标签、编目、创作人员、笔记及来源分片绑定到同一个 Git revision。页面首次读取后固定该快照；每个发布资源与基础详情均校验 Git blob SHA，不混用其他发布的 slot。旧资源缺失或校验失败时重新检查根清单；只有确认新 revision 才启动恢复。

恢复保留查询、筛选、排序、页码和稳定作品 ID 选择。基础作品和正式作品的编辑窗口只恢复实际改动的字段，未改字段采用新发布值；必须核对差异并重新确认后才能保存。凭据、文件内容、原确认勾选不会持久化。无法自动恢复的窗口、文件输入或浏览器存储失败会阻止刷新并提供草稿导出。恢复失败时保留会话草稿，24 小时后不自动载入。

写入仍通过现有来源版本校验和原子提交；发布回退也不赋予旧页面覆盖新来源的能力。正式作品的完整领域事件审计属于后续批次，本批只增加其提交回执。

## 保存与发布状态

保存成功生成含 operation ID、逻辑 revision、Git commit 和时间的公开回执，浏览器保留最近 30 条。页面显示最近 5 条的等待发布、发布中、已生效、失败或暂无法确认状态。仅当线上 `deployment.json` 的 revision、祖先提交或明确操作记录包含回执时，才标记已生效；后续合并发布可以同时覆盖此前多次保存。

待发布状态参考公共 Actions API 和提交祖先比较。API 不可用显示“暂无法确认”，不伪报成功；没有进行凭据上传。回退后的部署携带回退元数据，未包含的既有回执显示线上已回退。回执是当前浏览器的辅助记录，仓库中的保存提交和基础库事件仍是持久记录。

## 构建、发布与回退

`pages.yml` 负责验证与构建，可以取消同分支过时构建；不会撤销已经保存的数据。`pages-deploy.yml` 串行发布，禁止取消进行中的部署。自动发布只接受同仓库、成功的 main 构建，并在下载后再次核对 main；落后的构建被跳过。

回退使用成功构建的 `github-pages` artifact，保留期为 14 天。通过 GitHub Actions 的 **Deploy verified catalogue release → Run workflow** 输入目标成功 main 构建的 `run_id`：

1. 保持 `dry_run=true`，只下载、验证来源和哈希、解包，完成演练，不改变线上。
2. 确认目标后用相同 `run_id`、`dry_run=false` 发布该制品。此操作只改变 Pages，main、较新保存和审计记录不回退。
3. 恢复当前版本时重新运行 main 的构建工作流，让最新成功构建正常发布。

PR、失败构建、其他工作流、其他仓库及不安全归档均不能发布。旧制品必须具有匹配的部署与目录清单；过期制品需重新构建，不绕过验证。隔离测试验证旧制品发布与较新保存互不影响；不为测试实际回退生产站点。

## 验证

`tests/release-consistency.test.mjs` 覆盖共享快照、旧分片、哈希、回执祖先关系、失败/未知和回退状态。`tests/test_pages_promotion.py` 覆盖可信构建选择、隔离回退、来源一致性及恶意归档。`tests/browser/release-recovery.test.mjs` 在 CI Chromium 中打开实际基础库页面，覆盖跨发布翻页、稳定 ID 选择、编辑草稿恢复和会话存储失败；所有写入使用隔离模拟服务。
